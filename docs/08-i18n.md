# 08 — Le multilingue (FR / EN / DE)

Le site est pensé pour **trois langues**. Ce chapitre explique comment ça marche. Le mot technique pour « gestion des langues » est **internationalisation**, abrégé **i18n** (parce qu'entre le « i » et le « n » de *internationalization*, il y a 18 lettres).

## Les trois langues et leur statut

| Langue | Préfixe URL | Statut |
|--------|-------------|--------|
| **Français** | `/fr/…` | Langue principale, complète, indexée par Google. |
| **Anglais** | `/en/…` | Traductions publiées au fur et à mesure, indexée. |
| **Allemand** | `/de/…` | Préparé techniquement mais **caché du public** (non indexé) tant que les traductions ne sont pas finalisées. |

## Deux choses différentes à traduire

Il faut bien distinguer **deux niveaux** de traduction :

1. **L'interface** — les petits textes de l'« habillage » : les boutons (« Lire l'article »), les menus, les messages (« Rechercher… »), les libellés. Ils sont peu nombreux et fixes.
2. **Le contenu** — les articles eux-mêmes, longs, qui demandent une vraie traduction rédigée.

Ces deux niveaux sont gérés **différemment**.

## 1. La traduction de l'interface

### Côté serveur (au build) : `src/i18n/translations.ts`
Ce fichier contient un grand **dictionnaire** : pour chaque petit texte d'interface, sa version française, anglaise et allemande. Quand Astro fabrique une page anglaise, il pioche les versions anglaises.

### Côté navigateur (en direct) : `public/i18n-dict.js`
Subtilité de performance. Le site permet de **basculer la langue de l'interface sans recharger la page** (le bouton FR/EN). Pour cela, le navigateur a besoin d'un dictionnaire des traductions **en direct**. Ce dictionnaire est dans `public/i18n-dict.js`, chargé très tôt.

Comment ça marche concrètement :
- Les éléments à traduire portent une étiquette dans le HTML : `data-t="clé"` (pour du texte), `data-t-html="clé"` (pour du texte avec mise en forme), `data-t-placeholder`, `data-t-aria` (pour l'accessibilité)…
- Un petit script (dans `BaseLayout.astro`) parcourt la page, trouve ces étiquettes, et remplace le texte par la traduction de la langue choisie.
- Les **dates** sont aussi reformatées dans la langue active (« 24 septembre 2026 » / « 24 September 2026 »).

> **Pourquoi externaliser ce dictionnaire dans un fichier à part ?** Pour la performance : plutôt que de répéter ce dictionnaire (~10 ko) dans *chaque* page HTML, on le met dans **un seul fichier** que le navigateur télécharge une fois et garde en cache pour toutes les pages suivantes. C'est une optimisation détaillée au [chapitre 12](12-performance.md).

## 2. La traduction du contenu (les articles)

Les traductions d'articles vivent dans des dossiers séparés :
- `src/content/blog-translations/en/` — anglais.
- `src/content/blog-translations/pt-br/` — portugais brésilien (préparé, non publié).

Chaque fichier de traduction contient le **titre, le résumé, les métadonnées SEO, la FAQ traduits**, et le **corps de l'article en anglais**. Il est **relié à l'article français d'origine** par son nom de fichier (ou un champ `frSlug`).

Astuce intéressante : si une traduction est marquée **`draft: true`**, elle est considérée comme **inexistante** ; la page anglaise affiche alors le **contenu français** avec un petit bandeau « traduction en cours ». Ça permet de préparer des traductions à l'avance et de les publier d'un coup en retirant le `draft`.

## Les « slugs localisés » (adresses traduites)

Pour le référencement anglais, il vaut mieux que l'adresse soit **en anglais** : `chess-and-women` plutôt que `echecs-et-femmes`. Le système gère ça :

- Une traduction anglaise peut définir un champ **`enSlug`** (ex. `chess-and-women`).
- La page anglaise est alors générée à l'adresse `/en/blog/chess-and-women/`.
- L'ancienne adresse `/en/blog/echecs-et-femmes/` est **automatiquement redirigée** vers la nouvelle (via `enSlugRedirects()`, voir [chapitre 05](05-pages-routes.md)).

La fonction `getEnSlugMap()` (dans `src/utils/blog.ts`) construit la correspondance « slug français → slug anglais » utilisée partout.

## Basculer une adresse d'une langue à l'autre

Le petit fichier `src/utils/lang-paths.ts` contient `swapLangPrefix()`, qui transforme une adresse d'une langue en son équivalent dans une autre langue. Exemple : `/fr/blog/echecs-et-flow/` + cible « en » → `/en/blog/echecs-et-flow/`. C'est utilisé par le sélecteur de langue et par les balises `hreflang` (voir ci-dessous).

## Dire à Google quelles langues existent : `hreflang`

Quand une page existe en plusieurs langues, il faut **prévenir Google** pour qu'il propose la bonne version au bon visiteur (et ne considère pas les traductions comme du contenu dupliqué). Ça se fait avec des balises **`hreflang`** dans le `<head>` :

```html
<link rel="alternate" hreflang="fr" href="…/fr/blog/x/" />
<link rel="alternate" hreflang="en" href="…/en/blog/x/" />
<link rel="alternate" hreflang="x-default" href="…/fr/blog/x/" />
```

`x-default` désigne la version par défaut (ici le français). Ces balises sont générées par `BaseLayout.astro`. Cas particulier : les articles de **Grand oral** n'existent qu'en français ; pour eux, on n'émet **pas** de `hreflang` anglais/allemand (sinon on pointerait vers des pages inexistantes).

## La rubrique « Grand oral », exception française

Le Grand oral est une épreuve **du baccalauréat français** : ces articles n'ont aucun sens en anglais ou en allemand. La fonction `isFrenchOnlyPost()` les marque comme « français uniquement », et `filterPostsForLang()` les **exclut** des versions anglaise et allemande.

## Les menus par langue

Le fichier `src/data/site.ts` définit **trois menus de navigation** distincts : `navigationLinks` (français), `enNavigationLinks` (anglais), `deNavigationLinks` (allemand). Chacun avec ses libellés traduits (« À propos » / « About » / « Über uns »).
